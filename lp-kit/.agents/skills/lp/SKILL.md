# lp — 資料から、賞を狙えるLPまで

ユーザーは商品・目的・手元の資料を渡すだけでよい。参照サイト、技術、部品、使う専門Skillは AI が選び、実装・採点・磨き直し・実表示の確認まで終える。

## 最初に読むもの

このSkillは `lp-kit/.claude/skills/lp/` にある。`lp-kit/` を基準に次を読む。

1. `QUALITY_BAR.md` — 合格ラインと磨き直しのループ。**作り始める前に読む**
2. `references/component-catalog.md` — 参照サイト集と部品集。必要なものだけ使う
3. `references/motion-roles.md` — セクションの役割ごとの動き
4. ユーザーが渡した資料。既存のブランド資料・`DESIGN.md`・既存LPがあればそれも

## 使う専門Skill（必要な工程でだけ）

| 工程 | Skill | 使う時 |
|---|---|---|
| 中身を固める | `nattoku` | 受け手が価値・証拠・条件を理解して決められるかを点検する |
| 腹落ちの一撃 | `haraochi` | 「なるほど」と思わせる1点を設計する |
| 参照を選ぶ | `shakuyo` | 狙う印象から、異業種を含む参照ブランド・LPを選び、共通する文法を抜き出す |
| 参照を実測する | `extract-design` | 参照URLの色・書体・余白・動きを実測する（`designlang` CLI が使える時） |
| 参照を検索する | （外部）[Fudge](https://design.withfudge.com/) | Fudge の MCP が繋がっている時だけ使う。無ければギャラリーサイトをブラウザで開いて撮影する |
| 見た目を作る | `design-taste-frontend` | テンプレート臭のないLPを実装する |
| 見た目を直す | `refactoring-ui` | 階層・余白・色・影の具体的な直し |
| 動きを作る | `oil-motion` | 生成動画を使うスクロール演出。**有料の動画生成APIが要る**ので、使う前にユーザーに確認する |
| 直しを集める | `akaire` | ユーザーが画面上で囲んでメモした指摘を、位置つきで受け取る |

## 手順

1. **依頼を固める**: 対象者、見た後にしてほしい行動（主CTA）、入力資料、作る場所、公開範囲を資料から抜き出す。資料で分かることは聞き返さない。
2. **作業フォルダを作る**: `python3 scripts/new_lp_workspace.py --name "<商品名>" --source "<資料>" --audience "<対象者>" --cta "<主CTA>"`。`workspaces/<商品名>/` に5つの記録ファイルができる。同じ名前があれば上書きしない。
3. **商品を固める**: Before / After、約束、証拠、含むもの、含まないもの、価格、CTA を `01_LP_BRIEF.md` に書く。結論を変える事実だけユーザーに聞き、文章や配置の選択は AI が進める。
4. **作り手と受け手を決める**: 同じファイルに、デザイナー人格（肩書きでなく「何を見て、何を削り、何を選ぶか」）と、受け手のペルソナ（決める人と使う人を最低1人ずつ。見る環境・知りたいこと・不安・離脱する理由）を書く。社内の言葉は受け手の言葉に訳す。
5. **参照を集める**: `shakuyo` で狙う印象を1〜2語に決め、受け手・主CTA・価格帯が近い実在のLPを2本と、**最近の Awwwards Site of the Day を1本**選ぶ。実際に開いてファーストビューを1枚ずつ撮る（`refs/` に置く）。URLや「高級感」のような形容詞だけで次へ進まない。
6. **完成像を固める**: PCのファーストビュー・中盤の1セクション・スマホ（375px）の3画面を完成像として決める。方向が決まっていなければ、はっきり違う3案を作って1つ選ぶ。この時点で「署名の瞬間」（このLPにしかない印象的な1場面）を1行で書く。
7. **借りる範囲を残す**: 参照画像、借りる構図・書体・余白のリズム・動き、借りない範囲、ライセンス、有料かどうか、追加する依存を `03_REFERENCE_CONTRACT.md` に書く。
8. **実装する**: 作る場所のリポジトリが決まっていればその技術に合わせる。決まっていなければ `workspaces/<商品名>/site/index.html` に、ブラウザで開ける形で作る。構成案・プロンプト・Markdown だけで終わらせない。
9. **完成像との差を潰す**: 同じ画面幅で完成像と実装を並べ、構図 → 文字とリズム → 画像と動き の順に3回直す。
10. **賞の基準で採点し、合格まで磨く**: `QUALITY_BAR.md` に従う。既定は**標準モード**（別文脈の審査員1人が3つの視点で採点・上限3周・目安30〜40分）。ユーザーが「本気モードで」と言った時だけ、審査員3人を同時に呼び、上限8周にする。`node scripts/check-lp.js` で撮影・機械検査し、採点が返ったら直す前に `05_QUALITY_SCORECARD.md` に点を書き、下げている箇所トップ3だけ直して撮り直す。
11. **最終確認**: PC・375px・キーボード操作・動きを減らす設定・CTA のリンク先を実際に確かめ、`04_VERIFICATION_RECORD.md` に結果を書く。
12. **公開は分ける**: ローカルで開けるところまでが AI の仕事。一般公開・本番への反映・広告からの流入は、ユーザーが決めてから行う。

## 完了の条件

- [ ] 5つの記録ファイル（Brief・Design・Reference・Verification・Quality Scorecard）が同じ作業フォルダにある
- [ ] Before / After、約束、証拠、価格、CTA が矛盾していない
- [ ] 完成像3画面が実画像で決まっていて、署名の瞬間を1行で言える
- [ ] LP がブラウザで開ける
- [ ] `check-lp.js` が `"ok": true`
- [ ] 審査員の加重平均が 8.0 以上で、7.0 未満の項目がない（上限の周で届かなかったら、点を盛らずにそう報告する）
- [ ] 最後の返答に、LP と記録ファイルのパス、最終の点、まだ承認されていない公開範囲を書いた

## よくある失敗

| 失敗 | 対処 |
|---|---|
| 構成案や Markdown で終わる | ブラウザで開ける LP と採点まで続ける |
| 自分で採点して甘い点で合格にする | 別文脈の審査員に、スクリーンショットだけを渡して採点させる |
| 参照を何本も撮る、撮影スクリプトを自作する、記録を最後にまとめて書く（時間がかかる） | 参照は3本・ファーストビューだけ。撮影は `check-lp.js`。点は採点が返った直後に書く |
| 全部を少しずつ直して点が動かない | 1周でトップ3だけ直す。1周で0.3点伸びなければ、構図・書体・署名の瞬間のどれかを作り直す |
| 演出を盛って、何の商品か分からなくなる | 5秒で「自分向けだ」と分かるかを受け手審査員に確かめ、邪魔な演出を削る |
| 部品集から大量に混ぜる | セクションの仕事を先に書き、必要な1つだけを使う |
| 商品が決まっていないのに見た目を磨く | `01_LP_BRIEF.md` に戻る |
| 汎用写真と箱と線だけで高級感を出そうとする | 商品の実画面・成果物の寄りの画像を最低1点ずつ用意する |
| 外部のコードや有料部品を、出典やライセンスを確かめずに入れる | `03_REFERENCE_CONTRACT.md` に書き、無料・バージョン固定・元に戻せるものだけ入れる。有料はユーザーに確認する |
| 自社の価格や小さな比較対象を価値として書き、値段の上限を作る | `nattoku` で数字の見せ方を点検し、変化の中身で書き直す |
| 8〜11px の補足文字、文字と箱だけの画面 | 本文16px以上・補足14px以上・12px未満は禁止。利用シーンの画像を最低1点入れる |

## 守ること

- 実績・顧客名・お客様の声・効果の数字・受賞歴を作らない。
- 技術や機能ではなく、受け手の Before / After と買うものを主役にする。
- 費用がかかる操作・一般公開・本番への反映・他人への送信は、ユーザーに確認してから行う。
