# 実例: 会計事務所の業務ダッシュボードの作り

この合宿の手順は、実際にある会計事務所の業務ダッシュボードをAIと作ったときに回ったものです。ここでは**構造と考え方だけ**を紹介します。

リポジトリは非公開です。当日の講義で実物をお見せします。

## 何を作ったか

「顧客 × サービス × 期間 × 工程」の進捗を横断で見るダッシュボード。それまで業務ごとにスプレッドシートのタブが分かれていて、横断して見られなかった状態を置き換えるものです。

## リポジトリの形

```
（実案件リポジトリ）
├── docs/       設計ドキュメント（source of truth）+ HTMLプロトタイプ
├── web/        アプリ本体
├── supabase/   DBのスキーマとマイグレーション
└── secrets/    秘密情報の置き場（gitには入らない）
```

**`docs/` が先にあり、コードが後から付いてくる**形です。ここが普通の開発と違うところです。

## docs の中身と役割

| ファイル | 役割 | ポイント |
|---|---|---|
| `schema.md` | データモデル | **変更の履歴と「なぜそうしたか」が番号付きで残っている**。あとで同じ議論をやり直さない |
| `ui-guidelines.md` | 画面作りの原則 | 壁打ちで出た指摘を一般ルールに直して蓄積。「同じ指摘を二度しない」 |
| `infra.md` | 実行環境 | どこで動かすか、秘密情報をどこに置くか |
| `roadmap.md` | 実装スライス | **番号＝実施順**。1スライス＝1 PR |
| `data-sources.md` | いまのデータの在りか | 移行はしない。設計の出典として記録 |
| `meetings/` | 議事録 | 1会議1フォルダ。当時の設計メモもここ |

## プロトタイプが先にある

`docs/prototype.html` が**本番UIのリファレンス**になっています。実装するときは、これを手本に同じ見た目・操作を再現します。ゼロからUIを考え直さない、という指示がプロジェクトの規約に書かれています。

これが効くのは、**「見た目を決める会議」と「実装する作業」を分けられる**からです。

## CLAUDE.md の「作業前に読む」

プロジェクトの指示ファイルに、**着手前に読むドキュメントの一覧**が書かれています。AIはこれに従って、スキーマとUIガイドラインを読んでから手を動かします。

結果として、**同じ指摘を繰り返さなくなります**。これが後半の速度に効きます。

## スライスの回し方

1. ロードマップから次を1つ選ぶ
2. 小さく実装する
3. 実際に動かして確認する
4. PRを出す
5. レビューを受けて直す
6. マージして次のスライスへ

このループを、番号順に淡々と回します。**手前で価値が出る順に並べてある**ので、途中で止まっても、その時点で使えるものが残ります。

## この合宿に持ち込んだ考え方

| 実案件での実践 | 合宿での対応 |
|---|---|
| Artifactsで画面を先に作る | Step 2 |
| ER図で漏れを潰す | Step 3 |
| スキーマ確定後にロードマップを書く | Step 4 |
| 外部連携のキーを先に棚卸しする | Step 5 |
| `docs/`と`CLAUDE.md`を整えてから実装する | Step 7 |
| スライス→PR→レビュー→マージを回す | Step 8 |

## 持ち込まなかったもの

- 顧客名・担当者名・スプレッドシートのID・ドライブのID・本番URL
- 実際の業務固有の工程名や判断ルール
- 本番の接続情報

合宿で作るのは、**自社の業務に合わせた別物**です。この実例は「こうやった」の参照として使ってください。
