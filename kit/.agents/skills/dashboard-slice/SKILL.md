# dashboard-slice — 1スライスを実装する

たとえるなら、**1皿ずつ出すコース料理**。1皿作ったら味見して出す。全部まとめて作らない。

最初のスライス（S1: ログインして一覧が見える）は`dashboard-auth`の手順で作り、PRから先をこのスキルで閉じる。

## 手順

1. `docs/roadmap.md`から**次にやる1つ**を選ぶ
2. 実際に動く最小の変更を書く
3. **動かして確認する**（画面を開く。テストがあれば回す）
4. 差分を見る（変えたファイルと中身）
5. ブランチを切ってPRを作る。本文に「何ができるようになったか」と「確認方法」を書く

   ```bash
   git switch -c s2-edit
   git add -A && git commit -m "feat: 1件を開いて編集できる"
   git push -u origin s2-edit
   gh pr create --fill
   ```

6. レビューを受けて直す（AIに「このPRをレビューして」と頼むだけでもよい）
7. マージして（`gh pr merge --squash`）、`docs/roadmap.md`の状態を更新する。DBの変更があれば`dashboard-deploy`の順序で本番へ出す

## 守ること

- **1スライス1PR。** 関係ない修正を混ぜない
- **完了と言う前に実物を見る。** ビルドが通ったは完了ではない
- 失敗したら、まず再現する。再現できたら原因を1つに絞る
- 途中で気づいた別の課題は、直さずに`docs/roadmap.md`へ足す

## 終わりの状態

- マージされ、ローカルで動いている
- `docs/roadmap.md`の該当行が「済」になっている
- 次のスライスが1つに決まっている

## つまずき

| 症状 | 対処 |
|---|---|
| 変更が大きくなりすぎた | 途中でも割る。「見た目」と「機能」は分けられる |
| テストが無い | 確認手順をPRの本文に書く。それが確認の記録になる |
| 何度も同じエラー | エラー文をそのまま貼って、再現手順を先に固める |
