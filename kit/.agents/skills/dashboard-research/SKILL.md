# dashboard-research — 研究する（段階2）

たとえるなら、**段ボールの試作を一級建築士に見てもらう**。「ここは使いにくい」「この情報はどこに入る？」「この扉は誰でも開けられるけど大丈夫？」と、素人では気づけない所を洗い出してもらう。

**使うモデル: いちばん賢いモデル**（Codex: Astra、Claude: Opus）。詳しくは `ai-setup`。

## 手順

1. 材料を全部読む: `mvp/index.html`（開いて触る）、`docs/log.md`、あれば `README.md`
2. 次の観点ごとに、MVPの弱い所と、良くする方法を調べる

| 観点 | 問い |
|---|---|
| 使う人 | 誰が、いつ、何を見て、何を決めるのか。いちばん大事な操作は何か |
| 画面と操作 | 迷う所、押す回数が多い所、見落とす所はどこか |
| データの形 | 画面の情報はどんな表（テーブル）とつながりに分かれるか。履歴や状態は要るか |
| 権限と安全 | 誰が見てよく、誰が直してよいか。ログインは要るか。消してはいけないものは何か |
| 運用 | 誰がデータを入れ、いつ更新するか。今のスプレッドシートからどう移るか |
| 範囲 | 今日作るべき最小の範囲はどこまでか。今日やらないものは何か |

3. **ユーザーしか知らないこと**は、`grill-with-docs` の型で、番号付きの質問にまとめて一度に聞く（推奨回答つき）
4. 結果を `docs/research.md` に書く
   - 観点ごとの「分かったこと」と「良くする方法」
   - ユーザーの答えと、そこから決まったこと
   - MVPから引き継ぐもの／捨てるもの
5. 決まったことは `docs/log.md` に `[決定]` として足す。困りごとと使う人は `README.md`、業務の言葉は `CONTEXT.md` に書く

## 守ること

- MVPのコードを直さない。研究は「見る・調べる・書く」だけ
- ログの要望を1つずつ扱う。扱わないと決めたものも、理由と一緒に書く
- 研究の結果は必ずファイルに残す。会話だけで終わると、次の段階のモデルに伝わらない

## 終わりの状態

- `docs/research.md` に、6つの観点それぞれの結論がある
- `README.md` に困りごとの1文と使う人、`CONTEXT.md` に業務の言葉が3つ以上ある
- ユーザーへの質問が全部片付いている（答えられないものは「未確定」）
